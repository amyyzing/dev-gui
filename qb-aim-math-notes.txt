QB AIM MATH NOTES
=================

CURRENT IMPLEMENTATION ADDENDUM - 2026-06-10
--------------------------------------------

The active implementation has moved from the old WR-only time-lead model:

    target(t) = receiverStart + wrVel * (t + leadDelay)

to the universal relative-intercept model:

    releasePredict = releaseOffset + SERVER_SYNC_DELAY

    A = originNow predicted to releasePredict
    B = receiver position predicted to releasePredict, with Y forced to WR_MAX_Y
    C = routeDir * CATCH_AHEAD_STUDS

    target(t) = B + wrVel * t + C
    ball(t) = A + (throwVelocity + flat(qbVel) * QB_INHERITANCE) * t + 0.5 * G * t^2

The key split is:

    release/server timing moves both QB origin and WR start
    catch-ahead is a spatial offset in studs
    QB movement after release is represented only through QB_INHERITANCE
    receiver movement during flight is represented by wrVel * t

The current default catch-ahead is 8.0 studs. Old saved lead-delay values in seconds are migrated by:

    catchAheadStuds = oldLeadDelaySeconds * 21

The older sections below describe the previous model and are useful for comparison, but the active code no longer uses leadDelayForFlightTime() or target(t + leadDelay).

File this describes:
page-1/qb-aim/logic.lua

This is a plain-English and math breakdown of the current QB aim solver. The goal is to make it easier to tell whether the math itself is wrong, or whether the inputs feeding the math are wrong.


1. Main Goal
------------

The script tries to throw a football from the QB to a receiver so that the ball reaches the receiver's projected catch point at a fixed ball speed.

The important idea is:

    Find a time t where a ball moving at speed 95 can reach the same point the receiver is predicted to reach.

The solver is not supposed to pick "streak", "slant", or "diagonal" as special cases anymore. The receiver's actual XZ velocity should be enough. If the receiver runs north, east, diagonally, away, sideways, or toward the QB, that motion is represented by one vector.


2. Coordinate Meaning
---------------------

Roblox uses Vector3:

    X = left/right world axis
    Y = height
    Z = forward/back world axis

Most receiver movement math intentionally ignores Y:

    flat(v) = Vector3.new(v.X, 0, v.Z)

That means the receiver is treated as moving only on the field plane. The catch height is forced separately to WR_MAX_Y.


3. Constants Used By The Solver
-------------------------------

Current constants:

    BALL_G = 28
    G = Vector3.new(0, -28, 0)
    MODEL_BALL_SPEED = 95
    REMOTE_DISPLAY_POWER = 100
    DEFAULT_WR_MAX_Y = 14.00
    WR_MAX_Y = slider-controlled, default 14.00
    WR_LEAD_DELAY = slider-controlled, default 0.38
    QB_INHERITANCE = 0
    MIN_T = 0.35
    MAX_T = 6
    INTERCEPT_SCAN_DT = 0.025
    INTERCEPT_BISECTION_STEPS = 12
    GLOBAL_MIN_ANGLE = -5 degrees
    GLOBAL_MAX_ANGLE = 55 degrees

Important split:

    Local math speed = 95
    Remote power sent = 100

So the script solves the arc using 95, but still sends 100 to the server remote.


4. Ball Motion Equation
-----------------------

The script models the ball with constant gravity:

    ball(t) = origin + worldVelocity * t + 0.5 * G * t^2

Since G = (0, -28, 0):

    ball(t).X = origin.X + worldVelocity.X * t
    ball(t).Y = origin.Y + worldVelocity.Y * t - 14 * t^2
    ball(t).Z = origin.Z + worldVelocity.Z * t

This is normal constant-acceleration projectile motion.


5. Receiver Target Equation
---------------------------

The receiver target is:

    receiverStart = Vector3.new(receiverRoot.X, WR_MAX_Y, receiverRoot.Z)

But if the solver is previewing or waiting for the throw animation release, it first predicts where the receiver will be at release time:

    receiverReleasePosition = receiverRoot.Position + wrVel * releaseOffset
    receiverStart = Vector3.new(receiverReleasePosition.X, WR_MAX_Y, receiverReleasePosition.Z)

Then the catch target at flight time t is:

    target(t) = receiverStart + flat(wrVel) * (t + leadDelay)
    target(t).Y = WR_MAX_Y + C1_SOLVE_Y_BIAS

Since C1_SOLVE_Y_BIAS is currently 0:

    target(t).Y = WR_MAX_Y

So from the current moment, the total receiver prediction time is:

    totalReceiverPrediction = releaseOffset + t + leadDelay

For preview before release:

    releaseOffset is usually THROW_ANIMATION_RELEASE_WAIT, about 0.2667 seconds.

For final throw right at release:

    releaseOffset is usually 0.


6. Lead Delay
-------------

WR_LEAD_DELAY is not pure projectile physics. It is an extra prediction pad.

Current function:

    leadDelayForFlightTime(t) =
        WR_LEAD_DELAY * smoothstep(0.70, 1.35, t)

Meaning:

    if t <= 0.70:
        leadDelay is about 0

    if t >= 1.35:
        leadDelay is the full WR_LEAD_DELAY

    between 0.70 and 1.35:
        leadDelay smoothly ramps from 0 to WR_LEAD_DELAY

With default WR_LEAD_DELAY = 0.38:

    short throw, t = 0.50:
        leadDelay ~= 0.00

    medium throw, t = 1.00:
        leadDelay is partial

    longer throw, t = 1.35+:
        leadDelay ~= 0.38

Why this exists:

    In a perfect physics-only model, extra lead delay should be 0.

Why it may still be needed:

    The game/server/animation timing may mean the remote aim point is consumed later than the local solver thinks.
    The receiver position/velocity data may lag behind the real server state.
    The throw may not actually spawn exactly at the local origin/timestamp the script assumes.

Why it can feel wrong:

    Any nonzero leadDelay moves the target farther along the receiver velocity.
    Extra target movement is:

        extraLeadDistance = |wrVel| * leadDelay

    At 21 studs/sec and full 0.38 lead:

        extraLeadDistance = 21 * 0.38 = 7.98 studs

    That is a large amount of extra lead.


7. Receiver Velocity Estimation
-------------------------------

The solver does not use the receiver's raw velocity directly. It estimates a route velocity.

The tracker stores:

    rawVel = immediate frame velocity or AssemblyLinearVelocity
    vel = smoothed velocity
    ph = recent position history
    vh = recent velocity history
    accel = smoothed acceleration, currently stored but not used by the intercept solve

The code estimates least-squares velocity from recent position history:

    It fits X and Z position over time.
    The slope of X over time gives velocity.X.
    The slope of Z over time gives velocity.Z.

Simplified:

    lsVelocity.X = slope of position.X over recent samples
    lsVelocity.Z = slope of position.Z over recent samples

Then it blends:

    average recent velocity
    least-squares velocity
    previous smoothed velocity

The current route velocity then goes through routeSpeed().


8. Route Speed Function
-----------------------

routeSpeed(speed):

    clamped = clamp(speed, 0, 21)

    if clamped < 2.5:
        return 0

    if clamped >= 19:
        return 21

    otherwise:
        return clamp(clamped * 1.08, 2.5, 21)

This means:

    Very slow movement is treated as standing.
    Near sprint movement is treated as full route speed.
    Partial movement is slightly boosted.

Example:

    measured 10 studs/sec -> route speed 10.8
    measured 18 studs/sec -> route speed 19.44
    measured 19 studs/sec -> route speed 21

Why this can feel off:

    If the receiver is actually not at full route speed but their measured speed crosses 19, the solver snaps them to 21.
    If the receiver is changing direction quickly, smoothing can lag behind and aim where they were going a few frames ago.
    If AssemblyLinearVelocity is noisy, the route velocity can still be wrong even if the intercept equation is right.


9. Fixed-Speed Intercept Equation
---------------------------------

The solver wants a throw direction where:

    |throwVelocity| = MODEL_BALL_SPEED = 95

For a given candidate time t:

    inheritedVelocity = flat(qbVel) * QB_INHERITANCE

Currently QB_INHERITANCE = 0, so:

    inheritedVelocity = Vector3.zero

The target at time t is:

    target = receiverStart + wrVel * (t + leadDelay)

The ball equation is:

    target = origin + worldVelocity * t + 0.5 * G * t^2

But:

    worldVelocity = throwVelocity + inheritedVelocity

So:

    target = origin + (throwVelocity + inheritedVelocity) * t + 0.5 * G * t^2

Rearrange to solve the velocity needed for that time:

    throwVelocity * t =
        target - origin - inheritedVelocity * t - 0.5 * G * t^2

Define:

    neededDisplacement =
        target - origin - inheritedVelocity * t - 0.5 * G * t^2

Then:

    requiredVelocity = neededDisplacement / t

For this candidate time to be valid:

    |requiredVelocity| must equal 95

So the root equation is:

    F(t) = |neededDisplacement|^2 - 95^2 * t^2

Expanded using current target function:

    target(t) = receiverStart + wrVel * (t + leadDelay(t))

    F(t) =
        |receiverStart
          + wrVel * (t + leadDelay(t))
          - origin
          - inheritedVelocity * t
          - 0.5 * G * t^2|^2
        - 95^2 * t^2

The solver scans for t where F(t) crosses 0.


10. What F(t) Means
-------------------

If F(t) > 0:

    The required speed is greater than 95.
    The ball cannot reach that target at that exact time with speed 95.

If F(t) < 0:

    The required speed is less than 95.
    A speed-95 ball would have too much speed for that exact time.

If F(t) = 0:

    The required speed is exactly 95.
    That time is a valid fixed-speed intercept.


11. Root Finding
----------------

The solver:

    1. starts at MIN_T = 0.35
    2. scans to MAX_T = 6
    3. steps by INTERCEPT_SCAN_DT = 0.025
    4. checks for sign changes in F(t)
    5. refines sign-change intervals with bisection for 12 steps

Bisection only works when:

    F(lo) and F(hi) have opposite signs

That means the solver is strongest when F(t) crosses zero.

Possible edge case:

    If F(t) touches zero and turns around without crossing sign, sign-change scanning can miss it.

The code also checks "near" candidates, but the current near checks use targetMiss <= 0.05, which is very strict.


12. Candidate Construction
--------------------------

After choosing a candidate time t:

    requiredVelocity = neededDisplacement / t
    requiredSpeed = |requiredVelocity|
    direction = requiredVelocity.Unit

Then:

    throwVelocity = direction * 95
    worldVelocity = throwVelocity + inheritedVelocity

Since QB_INHERITANCE = 0:

    worldVelocity = throwVelocity

The remote aim point is:

    aimPoint = origin + direction * AIM_SCALE

where:

    AIM_SCALE = 1000

The script does not send C1 directly. It sends a far point in the throw direction.


13. Angle Limits
----------------

The throw direction is converted into an elevation angle:

    angleDeg = asin(direction.Y)

The candidate is rejected if:

    angleDeg < -5
    angleDeg > 55

This is a global sanity range.

Why this can feel off:

    If a real valid throw needs slightly above 55 degrees, the solver rejects it.
    If the best path is a high lob, it may not choose it.
    If the origin Y is wrong, the needed angle changes a lot.


14. Origin / C2 Height
----------------------

The throw origin is not always just the ball's position.

origin() starts with:

    basePosition = ball.Position or qbRoot.Position
    baseY = basePosition.Y

Then it tries to use the game's original Center.C2 Y:

    centerY = c2Y()

It accepts centerY only if:

    centerY >= baseY - 2.50
    centerY <= baseY + 8.00

If valid:

    origin.Y = centerY

If invalid or missing:

    origin.Y = ball.Position.Y

Why this can feel off:

    If Center.C2 is missing, hidden incorrectly, stale, or has a bad Y, origin.Y changes.
    A small Y error can change the required angle.
    If origin.Y is too low, the solver may aim too high.
    If origin.Y is too high, the solver may aim too low.


15. Release Offset
------------------

The script previews and throws around the throw animation.

Preview uses:

    releaseOffset = THROW_ANIMATION_RELEASE_WAIT
    THROW_ANIMATION_RELEASE_WAIT = 0.266666...

During final throw timing, buildReleasePlan recalculates with remaining release time until release.

Before release:

    origin is moved by QB horizontal velocity * releaseOffset
    receiver start is moved by WR velocity * releaseOffset

So the solver tries to aim for the state at actual ball release, not the state at button press.

Why this can feel off:

    If the animation release time is wrong, both origin and receiverStart are predicted to the wrong moment.
    If the server receives the remote later than expected, WR_LEAD_DELAY may need to compensate.
    If the local animation does not match the server release, the math can look right but throw wrong.


16. Preview Arc
---------------

The preview uses the plan's worldVelocity and time.

The actual preview points are based on the same projectile equation:

    p2 = origin
    p1 = ballAt(origin, velocity, plan.time)
    p3 = landing or later point

Conceptually:

    C2 should be the release/origin point.
    C1 should be the intercept/catch point.
    C3 is the later/landing part of the arc.

If C2 is wrong, the whole visual arc can look wrong even if C1 is reasonable.


17. What Is Truly "Universal" Here
----------------------------------

The universal part is the fixed-speed intercept:

    It does not care if the route is a slant, streak, diagonal, cross, comeback, or anything else.
    It only cares about:

        origin
        receiver start point
        receiver velocity
        ball speed
        gravity
        catch height
        time

If those inputs are correct, the equation is universal.

If it feels wrong, the most likely issue is not the equation. It is usually one of these inputs:

    receiver velocity
    receiver prediction delay
    release timing
    release origin/C2 Y
    real server ball speed
    real server gravity
    QB velocity inheritance


18. Why The Math May Feel Off Right Now
---------------------------------------

Most suspicious areas in current code:

1. WR_LEAD_DELAY is a tuning pad, not physics.

    The equation is clean, but leadDelay intentionally moves the target ahead.
    If it is too high, throws overlead.
    If it is too low, throws underlead.
    The taper prevents short-throw overlead, but mid/long throws still get the full extra pad.

2. routeSpeed snaps 19+ studs/sec to 21.

    This helps when the measured receiver velocity is slightly under true sprint speed.
    It hurts when the receiver is not actually sprinting or is changing direction.

3. Velocity smoothing can lag.

    Smoothing reduces flicker, but it can trail behind sudden cuts.
    That means a route change can be predicted too late.

4. QB_INHERITANCE is 0.

    If the real football inherits any QB velocity after release, the model is incomplete.
    Current code only predicts the origin forward before release.
    It does not add QB velocity to the ball after release.

5. Origin Y depends on Center.C2.

    If C2 is missing or stale, origin.Y falls back to ball Y.
    That changes the required vertical velocity and angle.

6. Near-root acceptance is very strict.

    The current near-root candidate requires targetMiss <= 0.05.
    That can reject usable approximate solutions.

7. Catch height is fixed.

    Receiver vertical motion is ignored.
    The receiver is always assumed to catch at WR_MAX_Y.
    If the real catch point is lower/higher, the throw will look vertically off.


19. Clean Version Of The Current Math
-------------------------------------

Definitions:

    A = origin at release
    B = receiver position at release, but with Y forced to WR_MAX_Y
    Vw = receiver route velocity, flat XZ only
    Vq = QB velocity, flat XZ only
    I = QB_INHERITANCE
    S = MODEL_BALL_SPEED = 95
    G = Vector3.new(0, -28, 0)
    L(t) = leadDelayForFlightTime(t)

Current target:

    T(t) = B + Vw * (t + L(t))

Current inherited ball velocity:

    H = Vq * I

Needed throw velocity at time t:

    U(t) = (T(t) - A - H*t - 0.5*G*t^2) / t

Valid intercept condition:

    |U(t)| = S

Root equation:

    F(t) = |T(t) - A - H*t - 0.5*G*t^2|^2 - S^2*t^2

Chosen throw:

    direction = U(t).Unit
    throwVelocity = direction * S
    worldVelocity = throwVelocity + H
    aimPoint = A + direction * 1000

Remote:

    FireServer(..., { Target = aimPoint, Power = 100 })


20. If I Were Debugging The Feeling
-----------------------------------

I would log these values per throw:

    plan.time
    plan.totalLeadTime
    plan.receiverPredictionDelay
    plan.receiverLeadDistance
    route velocity magnitude
    raw receiver velocity magnitude
    smoothed receiver velocity magnitude
    origin.Y
    Center.C2.Y
    target.Y
    angleDeg
    speedError
    targetMiss
    verticalVelocityAtCatch

The most useful comparison:

    actual receiver catch position
    predicted C1 target
    actual ball position when it crosses target Y

If predicted C1 is ahead of the receiver:

    reduce lead delay or route speed.

If predicted C1 is behind the receiver:

    increase lead delay, route speed, or account for server latency.

If C1 is horizontally right but vertically wrong:

    check WR_MAX_Y, origin.Y, ball gravity, and server speed.

If preview looks right but actual throw is wrong:

    check remote timing, server power conversion, release animation timing, and QB_INHERITANCE.


21. Biggest Current Hypothesis
------------------------------

The fixed-speed intercept equation is mathematically correct.

The parts most likely causing the "off" feeling are:

    1. WR_LEAD_DELAY is still a manual latency/timing correction.
    2. routeSpeed can overstate receiver speed.
    3. receiver velocity smoothing can lag during cuts.
    4. the real game may use a different release origin, gravity, speed, or QB velocity inheritance than the local model.

So the next mathematically useful improvement would not be another route bucket. It would be calibration:

    Record actual ball release position, actual ball velocity, actual receiver position at catch time, and compare them to the predicted plan.

Then tune:

    MODEL_BALL_SPEED
    BALL_G
    WR_MAX_Y
    WR_LEAD_DELAY
    THROW_ANIMATION_RELEASE_WAIT
    QB_INHERITANCE

against real observed throws.
